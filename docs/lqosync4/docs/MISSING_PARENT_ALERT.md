# Missing Parent Node alert — proposed LQoSync4 web contract

This contract covers a circuit whose Parent Node name and ID are both empty in LibreQoS v3 native input. It is a requirement for the planned Rust API and Leptos UI; neither exists in this checkout. The [current writer](../../../src/writer/v3network.rs) emits text alerts, and [native apply](../../../src/runner.rs) stops before writing LibreQoS input if any circuit would be omitted. Do not treat a successful shadow render as a successful apply.

## Who, what, when, where, why, and how

| Question | Answer |
|---|---|
| Who sees it? | An authenticated operator allowed to read LibreQoS status. The backend owns detection; the browser only displays the typed result. |
| What is wrong? | Show the number of **omitted circuits** and their underlying **rows**, then the affected Circuit ID and name. A multi-device circuit counts once as a circuit; its row count is the number of device rows omitted with it. |
| When does it appear or clear? | Show it when the selected target is `v3_network` and the latest completed native render omitted at least one circuit because its selected parent name and ID are empty. Refresh on a newer native result. Clear it only when a newer completed native render confirms zero such issues. A failed probe, failed collection, stale API response, or unavailable service keeps the last known native result with its age and does not claim recovery. If the target switches away from `v3_network`, hide the current warning as not applicable but retain it in run history. |
| Where is it visible? | On `/libreqos`, place a persistent alert directly under the title and `Sync now` row, before the Last sync card. Add a warning count and link to `/libreqos?issue=missing_parent` in the Dashboard LibreQoS card. The detailed list belongs below the alert and above the source preview. |
| Why does it matter? | LibreQoS v3 native circuits require a parent in the assembled topology. An omitted circuit would have no intended shaping entry in the new native input; native apply is therefore blocked. The current live file stays in place. |
| How does the operator resolve it? | Open the affected circuit details, set the static source row's `Parent Node` to a node that exists in the assembled topology (and use its matching ID when supplied), run a new shadow preview, then apply only after the issue count is zero. Do not guess an upstream or parent automatically. |

## Data and state contract

W01 SHALL define a typed `MissingParentIssue`; W06 SHALL emit it from the native renderer's circuit-level validation result, not by parsing `status.error`, `report.alerts`, or a TUI row flag. Today the writer groups rows by Circuit ID, sorts them, and selects the first row's parent for the whole circuit. `missing_parent` means that selected row has an empty parent name **and** empty parent ID, so the entire circuit is omitted. The issue's `row_count` is the number of rows omitted with that circuit, even if a later row has different parent fields. W06 SHALL validate that all rows of one circuit resolve to the same parent. A conflict emits a separate typed `conflicting_parent` issue and blocks native apply until corrected; shadow may retain the candidate for inspection. A supplied parent that cannot resolve is `unknown_parent`, and a valid parent ID with an empty display name is not `missing_parent`. Keep issue order deterministic. Do not send raw file paths, credentials, or full CSV contents in this diagnostic.

The proposed `GET /api/v1/libreqos/status` read model includes `snapshot_version`, `observed_at`, `target`, `mode`, `write_state`, `data_state`, and `missing_parent: { circuit_count, row_count }`. The Dashboard overview uses these totals from the same snapshot version. `write_state` distinguishes `candidate`, `blocked`, `written`, and `import_pending/imported` where the target supports them. `data_state` distinguishes `fresh`, `stale`, and `unavailable`. Persist the last completed native diagnostic separately from the latest attempt: the runner may stop at its probe before rendering, and the next status file can have an empty report. Keep the previous totals and time in that case, marked stale; do not replace them with zero. W01 SHALL freeze exact field and error names with E02 before coding the API.

The proposed paged `GET /api/v1/libreqos/issues?code=missing_parent&cursor=...&limit=...` returns `snapshot_version`, totals, a next cursor, and items containing `code`, `circuit_id`, `circuit_name`, and `row_count`. Bind the cursor to the completed **diagnostic generation** and filter so paging cannot mix native results; an unrelated operational snapshot update does not invalidate it. If that generation is no longer retained, return `409 page_expired` and restart paging. An issue list may contain many circuits; the status response carries counts, and the browser mounts only the visible page. A full issue list is never embedded in the Dashboard summary.

The Leptos `MissingParentAlert` shows concise copy such as **“1 circuit (1 row) has no Parent Node. Native apply is blocked.”** It also shows the exact cycle time, age, and `View affected circuits` link. On shadow mode, use a warning state and say the candidate is incomplete; on rejected apply, use a critical state and say the live LibreQoS input is unchanged. The banner is persistent until a newer clean cycle; a toast alone is insufficient. If data is stale, use an unknown/stale label and retain the last known count. Do not display `0` while loading or after an API failure.

`MissingParentList` shows one row/card per affected circuit with Circuit ID, name, row count, cause, and the instruction to select an existing topology node. It is read-only until an authorized, versioned source-edit workflow exists. Use text and an icon with color, a keyboard-focusable link, and a polite live announcement when the count changes. Do not announce every poll. At phone width, stack the title, count, time, and link without horizontal page overflow.

## Implementation and verification handoff

1. **Middle layer (W01):** Freeze typed issue and snapshot DTOs. Persist the last completed native diagnostic and its time across failed attempts; expose counts and paged details by diagnostic generation. Keep the current string alerts for CLI/status compatibility. Read cached state in HTTP handlers; do not run a router scan per request.
2. **Core and frontend (W06):** Emit typed issues from native validation; block native apply on mixed-parent rows of one circuit and show their separate `conflicting_parent` issue. Render the Dashboard count and `/libreqos` banner/list from typed API data. Link `?issue=missing_parent` to the filtered issue list. Never infer apply success from a file write or an empty HTTP error.
3. **Verifier:** Check one row, two rows of one circuit, conflicting parents, multiple circuits, unknown parent, valid ID with empty name, shadow candidate, rejected apply with prior native file unchanged, recovery after explicit parent, probe failure after an earlier alert, target switch, stale/unavailable data, 401/403, long names, pagination across version changes, keyboard use, and 320 px/200% zoom. Use synthetic fixtures only.

The current branch verifies the native apply guard in Rust tests. Browser rendering, API contract, authentication, and accepted-generation readback remain Phase 2 work.
